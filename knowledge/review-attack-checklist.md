# 攻めのチェックリスト — レビューで繰り返し出た指摘の型

> mission `20261028-codex-free-review` t002。外部レビュー (Codex) に頼らず、**作る段階で**よくある欠陥を潰すための型の一覧。
> Worker は PR を作る前に自己点検し（`agents/worker.md`「PR を作る前の自己点検」）、Director は card の書き方（`agents/director.md`）で最初から「脅威モデル」「壊れた入力のとき」を渡す。
> 各型は 見分け方 / 確かめ方 / 過去の実例（PR 番号と 1 行）。実例は過去のレビューで実際に出た指摘を一般化したもの。

## 使い方

1. 自分の変更を眺め、下の「見分け方」に 1 つでも当たる型を選ぶ（複数当たってよい）。
2. 「確かめ方」を**実際に実行**する（テストを書く・入力を作る）。読んで「大丈夫そう」で済ませない。
3. Result に該当した型と確かめたことを 1〜数行書く（例: `型1 fail-open: 型違い・欠けた欄・重複キー・途中切れの 4 入力で exit≠0 を確認`）。

型は網羅ではない。実物から足してよい。**同じ系統の指摘が 2 巡続いたら**穴埋めをやめて型 8 に切り替える。

---

## 型 1. 壊れた・想定外の入力で「通す側」に倒れる (fail-open)

- **見分け方**: 外部の出力・ファイル・JSON・環境変数を読んで、LGTM / done / 緑 / 許可 / 「問題なし」を決める変更。`.get(k)` / `or []` / `if d` / `except: pass` / 例外を握って既定値、がある。
- **確かめ方**: 入力を次の 4 形で壊して流し、**止まる側（拒否・保留・needs-director）に倒れる**ことを assert する。(a) 型違い（文字列のはずが数値・リスト）(b) 欠けた欄 (c) 重複キー・重複要素 (d) 途中で切れた出力（閉じない括弧・末尾が欠ける）。「空」「無い」と「読めない」を区別する（読めないを空に潰さない）。対照として健全な形が通ることも置く。
- **実例**:
  - #313: 自由文から findings JSON を拾う抽出が、壊れた外側の中の `{"findings":[]}` を採って P1 を「指摘なし」にした。括弧の対応で範囲ごと飛ばし、閉じなければ fail-closed。
  - #217: 検証のために足した `if d` が `blocked_by: [null]` を「依存なし」に潰した。要素を落とさず隔離して unmet に残す。
  - mission B の Codex 1 巡: 観測失敗・不正値を「許可」「不在」に潰す指摘だけで 6 件（LGTM は 1 本）。

## 型 2. 同じ規則の読み手が複数あり、1 つだけ検査が抜ける

- **見分け方**: 1 つの規則（依存が満たされた・状態・必須欄・engine 名・レコード形）を、複数の場所（pull / lint / dispatcher / status / task-graph / hook / 通知）が別々に読んでいる。新しい値・欄・状態を足す変更。
- **確かめ方**: 規則を読む場所を **grep で全部列挙して表にする**（実装から導く。docs の一覧は信用しない）。表の各行で新しい入力に同じ答えが返るテストを書く。入力の 3 形（無い・読めない・壊れている）を行ごとに流す。事前検査 (lint) と実行 (pull) の答えが揃うか。定義は 1 か所にして、コピーしない。
- **実例**:
  - #314 r4: 記録の形の検査が `.get` で型だけ見て欠けた欄を通し、読み手の `c['started_at']` が KeyError。必須欄タプルを 1 定義にして `k in data` で検査、欄を 1 つずつ落とす総当たり。
  - G3 (#266): mission.yaml が無い形で pull は止まり lint は通した。
  - assignment の撤去を変えたら消費者（is_idle / Rule 2 / task-graph pane_match / hooks）を全部洗う必要があった。

## 型 3. 時間・予算・上限が途中の呼び出しで効かない

- **見分け方**: timeout・リトライ回数・サイズ上限・予算を持つ処理で、内部で別のコマンドを呼ぶ・ループする・子プロセスを起こす変更。
- **確かめ方**: (a) 残り時間を**呼び出しごとに再計算**しているか（固定値を使い回すと合計で超える）。(b) `timeout` に `--kill-after` があるか。(c) `subprocess.run(timeout=)` は直接の子しか殺さない → 下の子孫が孤児で残る。`tests/proc_group.py` の `run_in_own_group()` / `kill_group()` を使い、**親を殺す前に**子孫を数える。(d) 上限ちょうど・上限+1・0 以下の値。
- **実例**:
  - #240: FIFO テストが赤のときタイムアウトで bash だけ殺され、下の `python3 -` が孤児で残った。
  - 実装 task の max は途中で延ばせず、実装 + CI 待ち + fix で 7200s を超えて tab が消えた（最初から 10800 を足す）。

## 型 4. 状態を先に書いてから失敗し、次回「変化なし」と見て直らない

- **見分け方**: 「処理した」印・fingerprint・offset・通知済み台帳・キャッシュ・throttle を、処理の**成否が分かる前**に書く変更。複数歩の書き込みで途中の 1 歩が済んでから別の歩が失敗しうる変更。
- **確かめ方**: 各歩の直後に失敗を注入し（kill / 例外 / 書き込み不可）、**次回の実行で収束する**ことを確かめる（再試行で直る・二重実行にならない）。印は**公開（外に出る成功）が済んでから**消す / 付ける。「済んだが耐久性（fsync）だけ失敗」は警告して最後までやる。失敗時のフォールバックの向きを決める（throttle の読み取り失敗は発火しない側）。
- **実例**:
  - #259: rename 後に親 dir の fsync が失敗して die し、state.yaml が移動済みの dir を指したまま、再試行でも直らなかった。
  - done の派生値（pr_number の伝播）をコミット点の前に書き、拒否された done が依存先に番号を残した。検査は dry_run で書き込みの前に。
  - hook の `stat -c` 失敗が「誤報 + throttle 無効」の二重故障になった。

## 型 5. 検査と読み手が別の欄・定義を前提にする

- **見分け方**: 「検査する関数」と「実際に値を使う関数」が別に書かれている。lint / store-check / schema と pull / dashboard。件数・集合・一覧が複数箇所にハードコードされている。
- **確かめ方**: 検査と読み手が**同じ 1 つの定義**（タプル・enum・schema）から作られているか。定義を変えたら両方が動く構造テストを置く。構造ガードは「検査した件数」を出して下限で FAIL にする（「見つからなかった」と「見ていない」を区別。worktree 配下だと絶対パス判定で全件除外される）。新しい lib・import は構造ガード（status の集合・再起動対象・JSON 読みの入口）を全部ローカルで回してから push。
- **実例**:
  - #229: 静的ガードが worktree で 0 件のまま PASS した。
  - #314 ×2: 新しい lib 1 つで構造ガードが赤になり CI を 1 周失った。
  - 並行 PR の構造ガードが衝突し、各 PR は緑でも先行 merge 後に main が赤くなった。

## 型 6. テスト・隔離環境から本番の registry / queue / tasks.json に書く

- **見分け方**: テスト・QA・probe・スクリプトが `plan.sh` / dispatcher / lib を呼ぶ。`CREWVIA_REPO_ROOT` や `AGENT_NAME` が環境から漏れる。fixture に lib をコピーする。
- **確かめ方**: 実行前後で本番の queue / registry / `tasks.json` が**変わっていない**ことを確認する（sha256 だけでなく、中身も開始時に保存）。env は明示的に渡す（`env -i` / `env -u AGENT_NAME`）。registry の場所は `registry_dir()`（queue の隣）1 か所から。隔離の lib コピーは `tests/fixture_tree.{py,sh}` の helper を使う。テストが呼ぶ gh・mux・git は stub / 隔離する。
- **実例**:
  - registry の根拠に `CREWVIA_REPO_ROOT` を使い、本番 task_count が 7→402 に汚染された。
  - #310: handoff テストが本番 `registry/handoffs/` に書いていた。
  - QA の ambient な `CREWVIA_REPO_ROOT` が本番を指していた。

## 型 7. パスに外から来た名前を使う

- **見分け方**: task id・slug・ブランチ名・ファイル名・worktree パス・外部ツールの出力を、パスやコマンドの引数に組み立てる変更。
- **確かめ方**: `..`・`/` 始まり・空文字・先頭 `-`・改行・非 ASCII・長大な名前を入れて、**根の外に出ない / オプションと解釈されない / 拒否される**ことを確かめる。ref 名は `git check-ref-format` を通す。名前は検証する関数（`check_*`）を 1 つ通す。`handoff_path` は絶対パスのみ。引数は literal の argv で渡す（`[..., *x]`）。
- **実例**:
  - 非 ASCII の名前・孤児の枠で新 lib が旧コードより厳しく、全 pytest でだけ露見した。
  - git の読み取り許可リストで、`git diff` / `blame` が既定で外部 diff・textconv を起動し、`fetch` が ref を消した（`--no-ext-diff --no-textconv` / `--no-prune`）。

## 型 8. 検出の穴埋めが続く → 経路そのものを判定に届かない形にする

- **見分け方**: レビューで**同じ系統**の P1 / P2 が 2 巡続いた。自由文の解釈・bash のパース・汚れた作業木の検出など「入力が無限に変わりうる」ものを正面から検出しようとしている。
- **確かめ方**: 穴を 1 つ塞ぐ前に自問する。(a) この経路を**判定（LGTM / done / 許可）に届かない形**にできないか（順序を変える・役割を比較専用に落とす・config で拒否する）。(b) **守る範囲（脅威モデル）**を `knowledge/` に書いたか（「正直な Worker のうっかりを守る。悪意ある回避は対象外。要るなら OS サンドボックス」のように）。(c) 部分解釈をやめ、「解釈不要の形だけ通す」に狭められないか。
- **実例**:
  - #313: cursor 経路の穴埋めが 6 巡。「Codex の後に走らせる」「判定に使わせない」の 2 つの設計変更で収束した。
  - #299: bash の読み取り専用 allowlist が 7 巡。脅威モデルを明記して収束。
  - task-graph: 観測失敗を空と読む 8 サイトを個別に直したが、「失敗を型で表す + ガード付き reader を唯一の入口 + 直接読みの機械検出」に変えて P1 が止まった。

## 型 9. 文書・コメントの断定が現状のコードと食い違う

- **見分け方**: 文書・コメント・docstring・PR 説明に「必ず〜」「既に無い」「常に新しい」「〜だけが読む」のような断定がある。変更がその前提に触れている。
- **確かめ方**: 断定を**実際に確かめる**（grep・実行・git で現状を見る）。前提が今も成り立つか、変更で崩れていないか。崩れていれば文書側かコード側を直す。書いた時点の記憶で「合っている」と済ませない。

## 型 10. 入力の型・欄の網羅検証が 1 形で終わっている

- **見分け方**: 読み込んだ record・JSON・YAML・引数を検査して使う変更。検査が健全な 1 形でしか試されていない。
- **確かめ方**: 型違い・欄の欠け・重複キー・不完全な record を **1 つずつ**流し、各々の結果（拒否 / 保留 / 通す）を assert する。欄ごと・型ごとに総当たりし、「まとめて 1 回」で済ませない。

## 型 11. 指紋・同一性の判定に入っているものと入っていないもの

- **見分け方**: 「同じ状態か」「変わったか」を fingerprint・hash・sha・mtime・`git status` で決める変更（作業木の汚れ、キャッシュの有効判定、再実行の要否）。
- **確かめ方**: 判定に **何が入っていて何が入っていないか**を列挙する（HEAD・clean な tracked・変更済み tracked・untracked・ignored）。入っていない種類を変えても判定が正しいか、1 種類ずつ変えて確かめる。

## 型 12. 状態を変えたとき、別のプロセスの読み手が追従するか

- **見分け方**: ファイル・台帳・card・registry の形や意味を変える変更。その値を別のプロセス（watchdog・dispatcher・hook・status・task-graph）が読む。
- **確かめ方**: その値の**読み手を別プロセスも含めて全部列挙**し（型 2 と併せる）、変更後の値を各読み手が正しく解釈するか、再起動が要るか（走り続ける旧コードが新しい形を読めるか）を確かめる。

## 重要度の基準

到達できる入力で **判定の誤り・データの消失・黙った誤動作** が起きるなら **P2 以上**。P3 に下げない。
P3 は、到達できない入力・見た目・保守性のように、実害の経路を書けないものだけ。

## 追加の確認（型ではなく習慣）

- **赤の実証**: 新しい検査・ガードは、欠陥版（変異）で**赤になる**ことを一度確かめる。緑のままなら、間違った理由で緑になっている。
- **テストの率**: race を含むテストは単独で 100 回回す。SIGKILL 直後は `wait_dead`。
- **数字は実測**: Result に書く件数・秒数は done の前に実測する。
- **私的な記録を貼らない**: 個人の memory の中身をそのまま文書に貼らず、型と教訓だけを一般化して書く。
